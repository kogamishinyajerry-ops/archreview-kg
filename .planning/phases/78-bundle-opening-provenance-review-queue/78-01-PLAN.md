# P78-01 Bundle Opening Provenance Review Queue Plan

## Objective

Turn P77's weak opening provenance bundle signal into a structured reviewer
triage queue while keeping it separate from package readiness and normal next
actions.

## Context

P77 added per-package opening provenance aggregation and weak coverage counts to
`handoff_bundle_index`. Managers can see weak packages, but the bundle artifact
does not yet provide a machine-readable queue dedicated to assigning reviewer
follow-up on weak semantic, measurement, or host-wall coverage.

## Tasks

1. Add RED tests for `opening_provenance_triage_queue` in bundle JSON plus
   Markdown/HTML rendering.
2. Implement a separate queue for weak coverage packages with reviewer actor,
   reason, coverage tuple, source artifact, and boundary warning.
3. Keep the existing package `next_action_queue`, package status, quality,
   signoff, manager, and archive semantics unchanged.
4. Update README, READINESS, CHANGELOG, ROADMAP, STATE, and Notion mirror.

## Success Criteria

- Weak opening provenance packages appear in `opening_provenance_triage_queue`.
- Strong packages are not queued.
- Markdown and HTML render the queue and preview-only boundary.
- Existing bundle next-action behavior remains unchanged.
- Ruff, mypy, targeted pytest, and full pytest pass.

## Guardrails

- Do not mutate handoff packages or source runs.
- Do not change `issues.json`, `review_state.json`, or rules engine behavior.
- Do not infer opening semantic, measurement, or host-wall provenance.
- Do not make weak coverage a package blocker or compliance finding.
- Do not make IfcOpenShell a hard dependency.
