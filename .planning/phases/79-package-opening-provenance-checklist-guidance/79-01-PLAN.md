# P79-01 Package Opening Provenance Checklist Guidance Plan

## Objective

Expose weak opening provenance coverage inside the package-local reviewer
checklist without changing checklist item counts, manager readiness, or source
run truth.

## Context

P77/P78 made weak opening provenance visible in bundle-level triage. A reviewer
opening a single handoff package still had to infer the same follow-up from the
manifest or bundle. P79 adds a guidance section to the copied package-local
`reviewer_task_checklist` so the reviewer sees missing opening provenance
signals in the artifact they already use for review notes.

## Tasks

1. Add RED tests proving `archkg handoff-package` writes package-local
   `opening_provenance_guidance` into `artifacts/reviewer_task_checklist.json`
   when opening provenance is weak.
2. Render an `Opening Provenance Guidance` section in
   `artifacts/reviewer_task_checklist.md`.
3. Preserve source-run checklist contents and package checklist `items[]` length.
4. Update roadmap, state, readiness docs, changelog, README, and Notion mirror.

## Success Criteria

- Weak opening provenance produces package-local checklist guidance with
  coverage counts and missing signals.
- Source run `reviewer_task_checklist.json` is unchanged.
- Package checklist `items[]` and summary counts are unchanged.
- Markdown guidance states preview-only boundary and package-local mutation
  policy.
- Ruff, mypy, targeted pytest, and full pytest pass.

## Guardrails

- Do not mutate source runs.
- Do not add checklist items or change manager readiness gates.
- Do not change rules engine, `issues.json`, or `review_state.json`.
- Do not infer opening semantic, measurement, or host-wall provenance.
- Do not treat weak coverage as compliance failure or BIM completeness failure.
