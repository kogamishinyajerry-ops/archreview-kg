# P71-01 Opening Semantic Provenance

## Objective

Make the P70 door/window opening semantics auditable in `layout_3d` and Viewer/Studio without introducing new recognition logic, IFC hard dependencies, wall void geometry, or rule-engine inputs.

## Context

P70 added `window_opening` only when a `Door` entity carries explicit graph evidence (`opening_kind` or `is_window`) and mapped it to `IfcWindow` in optional IFC preview export. The next small closure item is provenance: reviewers should be able to see why an opening is displayed as a door or window.

## Tasks

1. Add `properties.opening_semantic` to `door_opening` and `window_opening` layout objects.
2. Preserve explicit evidence keys/values for windows and record generic Door defaults for normal door openings.
3. Add an `Opening Semantics` section to `layout_3d_summary.md`.
4. Add `opening_semantics` data to the Viewer adapter and render it in Viewer/Studio.
5. Add regression tests for provenance, summary text, and Viewer rendering.
6. Update README, READINESS, CHANGELOG, ROADMAP, STATE, and this phase summary.

## Success Criteria

- A default `Door` maps to `door_opening` with provenance showing `entity_type=Door` and `explicit=false`.
- A `Door` explicitly marked as window maps to `window_opening` with provenance showing the source property and value.
- Viewer/Studio shows an `Opening Semantics` summary with explicit graph evidence boundary text.
- `layout.ifc` optional dependency behavior remains unchanged.
- `ruff`, `mypy archkg`, targeted tests, and full pytest pass.

## Guardrails

- Do not add wall void geometry or boolean subtraction.
- Do not add neural or heuristic window recognition.
- Do not promote opening semantics to `issues.json`, `review_state.json`, or rule-engine inputs.
- Do not make IfcOpenShell mandatory.
- Do not claim review-grade BIM or compliance conclusions.
